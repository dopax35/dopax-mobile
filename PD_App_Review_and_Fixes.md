# dopa-X / PDCollect — Usability, UI, and Stability Review

Reviewed both native apps (Android/Kotlin, ~16k lines; iOS/Swift) end to end: manifest/permissions, theme and design-system compliance, every consent/onboarding/settings screen, all five motor tests, the passive-collection services, Bluetooth integrations, and data-upload paths. This is a mature, actively-maintained research app (v3.7.20 on Android) with a lot of prior hardening already in place — the bugs found below are specific and mostly narrow, not systemic neglect. 22 fixes were made directly in the code. A handful of items are flagged for a product/clinical decision rather than fixed, since the right answer isn't a pure code question.

Real compilation/test execution wasn't possible in this sandbox (the project's bundled JDK and Android SDK are Windows binaries; the sandbox's own JDK is v11 vs. the project's required v17). Every fix was instead re-read in full after editing and cross-checked against sibling files and existing unit tests for consistency.

## Highest-impact fixes

**Android consent screen could crash, and even when it didn't, hid 2 of 3 pages of the consent document.** `ConsentActivity` rendered the PDF at `screenDensity × points/72`, which produces ~150MB *per page* on a typical high-density phone (three A4 pages ≈ 450MB of bitmaps held at once) — a near-certain OutOfMemory crash on the very first screen every new participant sees. Independently, the container showing the rendered pages had a hardcoded `300dp` height with no scrolling, so even without the crash, only the top of page 1 was ever visible — participants could check "I have read and understand" and sign without any way to see pages 2–3. Fixed both: pages now render at actual screen-width resolution, the container is scrollable, each page renders independently (one bad page no longer blanks the rest), and the Agree button is disabled with a visible error if the document fails to load.

**iOS consent screen's "scrolled to bottom" gate was completely disconnected.** The state variable existed and was being set, but nothing ever read it — the Agree button was always enabled, so a participant could tap through without reading anything, and the scroll-position tracking itself would have marked "scrolled" almost immediately on render even if it *had* been wired up. Rewired the scroll detection to genuinely compare content position against the viewport, and the button is now disabled until the participant reaches the bottom.

**Trail Making Test never recorded errors.** TMT is clinically scored on time *and* errors, but the wrong-target-detection method was fully written and never called from the touch handler — every session recorded exactly 0 errors, silently, since this was written. Wired it in, with edge-triggering so a lingering touch on a wrong target counts once, not dozens of times across touch-move events.

**A background thread leaked every time seven different Android screens were opened.** `DataManager` starts a live `HandlerThread` in its constructor that only stops via an explicit `closeAll()`. Settings, Data Export, Debug Preview, Questionnaire, Profile Setup, and Spiral Tracing all constructed one and never closed it — Settings' instance additionally holds ~11 open file writers via `initializePassiveLogs()`. Voice Sample had the same gap plus a genuine data-loss risk, since its writes are buffered and were never flushed. All seven now close cleanly on exit, matching the pattern the other screens already used correctly.

**iOS custom fonts and camera permission text were both broken.** The bundled Rajdhani/Outfit fonts were never registered in `Info.plist`'s `UIAppFonts`, so every headline styled with the app's custom type scale silently fell back to the system font — and separately, `Outfit-Medium` was referenced in code but the bundled file is actually `Outfit-Thin` (confirmed via the font's internal name table), so that style would have kept falling back even after fixing the registration. Also fixed: `NSCameraUsageDescription` told users the camera was "to scan documents" when it's actually used for on-device face-distance estimation — misleading permission text in a clinical-consent context.

## Other fixes

- **Voice Sample test read unfiltered live news aloud** to a population the app's own questionnaire screens for anxiety and depression. Added a keyword filter (Hebrew + English) that excludes headlines about death, violence, terror, or disaster before they can be selected as a reading passage, falling back to the existing curated stories.
- **Two dialogs stacked on top of each other** after finishing any Active Test (the encouragement "nudge" and the questionnaire prompt fired simultaneously) — the developer had left comments acknowledging this was unresolved. Now sequenced properly: the questionnaire prompt only appears after the nudge is dismissed.
- **Android login screen had no recovery path on failed sign-in** — a real auth failure (not user-cancel) left a blank screen with only a toast telling the user to "check logs." Now shows a plain-language message and closes cleanly so reopening the app retries, matching the existing cancel-path behavior.
- **iOS "Reset & Withdraw" undersold what it actually does.** The message didn't mention that this only deletes the on-device copy — already-uploaded research data isn't affected. A participant could reasonably believe withdrawing here erases everything everywhere. Copy now matches Android's more complete disclosure.
- **iOS `CloudUploader` leaked a `URLSession` + delegate per uploaded date** — delegate-backed sessions aren't released just because they go out of scope; needed an explicit `finishTasksAndInvalidate()`.
- **iOS background-upload loop ignored task cancellation** — `BGProcessingTask`'s expiration handler called `.cancel()` on the Swift `Task`, but nothing checked `Task.isCancelled`, so an upload run kept burning already-expired background time. Added the check.
- Two smaller correctness/cleanup items: a leftover duplicate `.setMessage(...)` call in Profile Setup (dead code, second call silently won), and a missing `timestamps`-array guard in `PDAlgorithms.spiralFeatures` that force-unwraps on two parallel arrays that are currently always kept in lockstep but aren't defensively guaranteed to be.

## Follow-up (July 2026): the six flagged items above

Every item flagged above got an explicit answer and, except the first, a code change:

- **Beanie**: confirmed intentional — the sensor "will be enabled shortly." Left exactly as-is, no code changes.
- **Screen Capture / "Visual Context"**: confirmed it was never supposed to take real screenshots — the intent was only a lightweight "did the screen change" signal, which `DataAccessibilityService`'s existing `ACTION_FOREGROUND_APP_CHANGED` broadcast already covers. Removed entirely — service, Settings toggle, constants, strings — rather than wiring up real screen capture.
- **Color palette**: Dopa-X (not `DESIGN.md`'s "Empathetic Anchor" spec) confirmed as current intent. Standardized both platforms on the four Dopa-X hues (blue `#2828C6`, blue_dark `#0F0F3D`, purple `#5B34A4`, orange `#FF5C35`) for brand-accent colors — charts, buttons, icons, the left/right ordinal coloring on bilateral motor tests — while deliberately leaving semantic status colors (success/error), traffic-light severity scales, and OS- or third-party-mandated colors (e.g. Google Sign-In) untouched.
- **TMT errors**: both platforms now track both clinically-relevant error types. Android gained lift-off detection, iOS gained wrong-target detection, and both write an identical 9-column schema (`...,wrong_target_errors,lift_off_errors,...`) to `tmt_results.csv`.
- **iOS Voice Sample**: built the missing screen from scratch — same RSS-fetch-with-distressing-content-filter and curated Hebrew fallback stories as Android, a 60-second `AVAudioRecorder` flow, and a `voice_log.csv` schema identical to Android's (`timestamp_ms,filename,story_headline,duration_ms`).
- **Debug trigger**: gated behind `BuildConfig.DEBUG`. Wired up in debug builds only; in release/participant-facing builds the invisible view is unclickable, unfocusable, and hidden, so it can no longer be triggered by an accidental tap.

## Follow-up (July 2026, round 2): build feedback

A real build caught two more things static re-reading hadn't:

- **Android build failure**: `VoiceSampleActivity.kt` called `.shuffle()` on the result of `.filterNot { }`, which returns an immutable `List` — `shuffle()` is `MutableList`-only, so this never compiled. Changed to `.shuffled()`, which returns a new shuffled list and needs no mutability.
- **Medication row "X" button was under the 48dp tremor-accommodation minimum**: root cause was the same in both places it appears (`SettingsActivity.kt` and `ProfileSetupActivity.kt`, which each have their own copy of the medication editor) — the button's `LinearLayout.LayoutParams` were constructed in code with a raw `100`, and LayoutParams built in Kotlin (not inflated from XML) take pixels, not dp. On a high-density phone like the Galaxy S25 that's roughly 33dp — noticeably under the 48dp minimum. Fixed by converting 48dp to pixels explicitly (`TypedValue.applyDimension`) and applying it to both width and height in both files. iOS has no equivalent bug: its medication list uses swipe-to-delete rather than an inline remove button, which doesn't have a small-fixed-size tap target to begin with.
- **iOS build failed with 39 errors** — nearly all "Type 'ShapeStyle' has no member 'dopaxOrange'" (etc.) scattered across totally unrelated views. Root cause was one real bug in `VoiceSampleView.swift`: `SimpleRSSParser` subclasses `NSObject` (needed for `XMLParserDelegate`), and it had declared its own stored property named `description` — which collides with `NSObject`'s own inherited `description` property. That single collision was enough to abort the module's type-check pass, which is why dozens of unrelated files suddenly couldn't resolve `Theme.swift`'s `Color` extension members. Renamed the property to `descriptionText`; nothing else needed to change.

## Follow-up (July 2026, round 3): login failures + build re-check

A user reported login issues on iOS with both Apple and Google sign-in:

- **Google Sign-In couldn't complete**: `Info.plist` was missing the `CFBundleURLTypes`/`CFBundleURLSchemes` entry for Google's reversed client ID. It was declared in `project.yml` but never made it into the actual shipped `Info.plist` (XcodeGen merges `project.yml`'s `info.properties` into the physical file at generation time, and that regeneration hadn't happened since the entry was added — the file was missing the key entirely). Without a registered URL scheme, iOS has nowhere to route Google's OAuth redirect back into the app: the user authenticates in the browser and the flow just dead-ends. Added the scheme directly to `Info.plist`.
- **Sign in with Apple could silently do nothing**: `LoginView.swift` used the real, native `SignInWithAppleButton` with empty request/completion closures, plus an invisible overlay `Button` on top meant to intercept the tap and hand off to `AuthManager`. Native control touch handling and a SwiftUI overlay's tap gesture don't have guaranteed precedence — the real button can swallow the tap into its own no-op handler instead of the overlay underneath, which matches exactly the kind of intermittent "nothing happens when I tap it" a user would report. Replaced it with a single, real button (same visual pattern as the Google button beside it) that directly and unambiguously calls the existing, already-correct `AuthManager.signInWithApple`.
- Checked and confirmed already correct, no changes needed: `AuthManager`'s nonce/SHA256 handling and Firebase credential exchange for both providers, `AppDelegate`'s URL-forwarding to `GIDSignIn`, and the Sign In with Apple entitlement.
- **Re-checked the previously-unresolved 36 "ShapeStyle has no member" build errors**: every one traces to a symbol (`dopaxBlue`, `dopaxOrange`, etc.) that `Theme.swift` already exposes through a complete `extension ShapeStyle where Self == Color` bridge, and there's no duplicate or conflicting declaration anywhere else in the project. The uploaded build log has no other error in it — these 36 are the only ones. The most consistent explanation is that the log reflects a build from before that bridge extension existed in the file; current source has nothing left to fix for this error set. Worth a clean rebuild (Clean Build Folder, delete DerivedData, re-run `xcodegen generate`) to confirm before writing this off.

## Follow-up (July 2026, round 4): Beanie re-enabled with on-device ML activity inference

Beanie was re-enabled on both platforms with a new feature layered on top: a bundled TFLite/CoreML model (`IMUTempClassifier_V5_I7T3P4` / `IMUTempClassifier_V5_250`) that classifies activity (Running/Walking/Sitting/Standing/Stairs) from a rolling 250-sample IMU window plus temperature and posture, shown as a third column on the Beanie vitals card. Reviewed both ports end to end for correctness, cross-platform consistency, and battery impact given most users won't have a Beanie paired most of the time.

**Android build was broken.** `BeanieService.kt` called `postureEngine.feedScaledImuSample(ax, ay, az, gx, gy, gz)` once per IMU sample — that method doesn't exist anywhere on `PostureEngine`; its only per-sample entry point is `process(samples: List<ImuSample>)`, which takes the whole batch and does its own raw→scaled conversion internally. This is a plain unresolved-reference compile error, not a runtime bug — the Android app could not have built at all. Fixed by calling `postureEngine.process(samples)` once per packet instead, matching how the same `samples` list is already used for CSV logging two lines above it.

**Inference window timestamps were wrong after the first ~40 seconds, on both platforms.** Each platform keeps a 1001-row IMU ring buffer feeding the model's most recent 250 rows, and stamps each inference with a `windowStartMs`/`windowEndMs` for the exported data. Both `imuWindowStartMs` (Android) and `imuWindowStartMs` (iOS) were only ever set once, at the moment the ring buffer went from empty to its first sample — once the buffer fills to capacity and starts sliding (which happens well before the first inference even fires), it never becomes empty again, so every single inference for the rest of the connection reports the same original connect-time timestamp as its window start, regardless of how long the connection has been running. Fixed on both platforms by keeping a parallel timestamp deque/array alongside the IMU ring buffer and reading the true start time off the last-250-sample slice actually fed to the model.

**Android's live activity/confidence forgot itself on every app reopen.** `BeanieStatusSnapshot` — the small object persisted to SharedPreferences so the dashboard has something to show immediately on resume, before the next live broadcast arrives — had no fields for activity label or confidence, so `MainActivity.syncBeanieUi()` always passed `null` for both on resume, and the new third column would sit blank until the next live update. Added `activityLabel`/`activityConfidence` as backward-compatible optional fields (existing call sites all use named arguments, so nothing else needed to change) and wired them through both the writer (`BeanieService.currentSnapshot()`) and the reader (`MainActivity.syncBeanieUi()`).

**iOS CSV wrote different decimal precision than Android for the same two columns.** `BeanieTemperatureReading.csvRow` formatted `heat_flux_cal_per_sec` at 4 decimal places and `ml_confidence` at 4 decimal places, while Android's `formatDouble()` writes every numeric column in `beanie_temperature.csv`, including those same two, at 2. Not a correctness bug, but a real cross-platform inconsistency in a file both platforms are supposed to produce identically — aligned iOS to 2 decimals for both.

**Flagged, not fixed — needs a product/ML-owner decision, not a code fix:**

- **Posture input is hard-zero on both platforms right now.** Android ported a full, real posture-tracking system (`PostureEngine.kt`: a Madgwick AHRS filter fusing accel+gyro into a gravity vector, plus a whole `PostureCalibrationProfile` persistence layer) — but nothing in the Android UI ever calls `applyCalibration()`, so `cal.isCalibrated` is always false and the model's posture input is always `[0,0,0,0]` by the code's own documented uncalibrated-fallback design. iOS's main app never got a Madgwick/calibration port at all — `BeaniePostureEngine.swift` is a bare history buffer, and its one call site passes zero args with a comment admitting as much ("uncalibrated zeros for now"). **This is fixable without guesswork**: the cloned reference project at `tmp/beanie_ios/BLEReader/PostureEngine.swift` (1199 lines) has a complete, working `MadgwickFilter` + `PostureEngine` + `PostureCalibrationProfile` — the same lineage Android's version was already ported from (Android's file cross-references "iOS PostureEngine.swift parity" throughout). Porting it properly is a bounded, known-good task, not a from-scratch build. Both platforms would then also need an actual calibration screen wired up, since neither's *main app* has one today — the reference project's own calibration flow lives inside its `ConnectView.swift`/`ConnectScreen.kt`.
- **The model's tSkin input is documented as "synthesized" but both platforms feed it the raw packet value.** `ActivityEngine.kt`'s own header comment said tSkin should come from `TskinSynthesizer`; in reality `BeanieService.kt` and iOS's `BeanieBluetoothService.swift` both pass the raw `sample.tskinC` straight from the packet parser, and Android's ported `TskinSynthesizer.kt` (483 lines) is never instantiated anywhere. Corrected the misleading comment. Worth knowing before wiring this up: the two cloned reference projects are on different lineages here. `tmp/beanie_android`'s reference still uses `TskinSynthesizer` (inside `EnvInference.kt`) as its live path — that's what Android's port faithfully carried over. `tmp/beanie_ios/BLEReader` has *both* `TskinSynthesizer` (inside `EnvInference.swift`) *and* a newer `ThermalEngine.swift` (self-documented "v3 — unified thermal processing pipeline," changelog references a v2) — and the reference app's actual BLE handling (`BLEReader.swift`) calls only `ThermalEngine.processSample(...)`, never `TskinSynthesizer`, directly. So a same-name port ("give iOS a TskinSynthesizer.swift to match Android") would likely be porting logic iOS's own reference lineage has already moved past. Whoever owns the model should confirm which version the training data was actually built from before either platform wires anything in.
- **A meaningful amount of ported Android backend has no UI consumer yet**: `ActivityInferenceManager`/`ActivityLogManager` (the ✓/✗ "confirm or correct this prediction" strip and its log), `MLPredictionStore` (a richer per-inference JSON record with the full 5-class probability vector, written continuously but never read back by anything — including any export path, so it accumulates on-device indefinitely), and `EnvInference`/`ChartUtils`/`LinearRegressor` (environment/history-chart support code). All of it is real, functioning, internally-consistent code — it's just not hooked up to any screen. The working UI for all of it already exists, just not in this app: `tmp/beanie_android`'s `ConnectScreen.kt`/`LiveScreen.kt`/`InsightsScreen.kt`/`DebugScreen.kt` (Jetpack Compose) and `tmp/beanie_ios/BLEReader`'s `ConnectView.swift`/`LiveView.swift`/`InsightsView.swift`/`DebugView.swift`/`AnalyticsView.swift` (SwiftUI) are the reference app's own screens for exactly this data. Porting them means either adopting Compose/introducing more SwiftUI-only screens into apps that currently use classic Android Views + a mix of SwiftUI, or re-implementing the same screens by hand in the existing UI style. Left as-is rather than building the missing screens, which would be new feature work beyond this review's scope.

**Housekeeping: the diff for this round was 208 files / ~67,000 lines before cleanup, for what is actually about a dozen files' worth of real change.** Nearly everything else was line-ending noise — most of the Android tree (and a chunk of the iOS tree) had been silently converted from Unix (`LF`) to Windows (`CRLF`) line endings, which makes every touched file look fully rewritten in a diff even when not one real character changed. Confirmed this was pure noise by diffing with whitespace ignored (208 files → 74, then → 12 once the two IMU-timestamp/compile fixes above are excluded) before normalizing every text file back to `LF` to match the repository's existing convention. No file content changed from this pass — only line-ending bytes. This should make the actual review for this round tractable for whoever reads the real diff next.

## What was already solid

Both platforms show real, prior investment in stability: Android's `BeanieService` and `HandTurningActivity` have careful GATT-lifecycle and TTS/sensor cleanup with defensive stale-callback guards; the changelog in `build.gradle.kts` documents a long history of real fixes (GATT leaks, NaN graph handling, Android 14 background-start restrictions, Samsung auto-rotate teardown); iOS's `DataManager` sidesteps the whole "leaked background thread" bug class by design (opens and closes a file handle per write rather than holding one open); permission-rationale copy throughout Profile Setup is unusually thorough and honest about what each permission does; and the study-withdrawal flow (once the iOS copy fix above lands) is honest about what it does and doesn't undo.

## Follow-up (July 2026, round 5): posture calibration, TskinSynthesizer wiring, and a systemic file-corruption cleanup

**Posture calibration is now real on both platforms.** Android already had a complete `PostureEngine` (Madgwick filter, axis-frame calibration math) but no capture UI, so nothing ever called `applyCalibration()`. Built `PostureCalibrationActivity` — a 5-step wizard (neutral/left/right/chin-down/look-up, each with a 3s get-ready countdown and a hold), reachable from a new "Calibrate Posture" button on the Beanie device picker screen, gated on a Beanie actually being paired. iOS had no calibration system at all — ported `MadgwickFilter`, `PostureState`, `PostureCalibrationProfile`, and a full `PostureEngine`-equivalent (`BeaniePostureEngine`, replacing the old zero-stub) from the Android/reference math, then built a matching SwiftUI `PostureCalibrationView` reachable the same way from Bluetooth Devices. Per instruction, no history/chart UI was built for posture on either platform — the calibration screens are the only new UI surface.

**`TskinSynthesizer` is now wired into inference on both platforms**, per instruction, despite iOS's own reference project having moved on to a newer `ThermalEngine`. Android's `TskinSynthesizer.kt` already existed but was never instantiated; it's now created once per `BeanieService` lifetime and its smoothed output feeds the model's tSkin input (raw `sample.tskinC` is untouched in the CSV — only the ML input is smoothed). Ported the same class to iOS (`TskinSynthesizer.swift`) and wired it the same way into `BeanieBluetoothService`.

**Beanie ML data now reaches the exported files on both platforms.** Android's zip builders (`zipYesterdayData`/`zipDateData`) now add a per-date `ml_predictions.json` entry (full probability vector + window bounds), since that store lives outside the per-date directory tree the zip otherwise walks. iOS needed no equivalent change — its per-date directory already contains the Beanie CSVs, and completing the (separately discovered) truncated `zipDate()` was enough for the whole directory, ML data included, to be zipped.

**A large, unrelated problem surfaced while verifying the above: dozens of files on both platforms had been silently truncated** — cut off mid-statement, sometimes mid-character — relative to their last real edit, with no compensating content. Root cause looks like a systemic failure in whatever process performed the earlier Beanie re-enablement pass; most affected files had nothing to do with Beanie (`Theme.swift`, chart views, motor-test screens, `Constants.kt`, layout XML, `Info.plist`, `AndroidManifest.xml`, `build.gradle.kts`). Neither app would have compiled in this state. Given the choice of fixing everything now vs. only the Beanie-touched files vs. just reporting it, the direction was to fix everything. That work is done:

- Restored ~35 purely-truncated files (zero lost content, safe to take verbatim from the last commit) across both platforms — chart views, motor-test activities/views, managers, models, resource XML.
- Found and stripped a second, distinct corruption pattern in 10 more files: hundreds of trailing NUL bytes appended after otherwise-complete, correct content (made `file` misidentify them as binary). `UserProfile.kt`, `ActiveTestsActivity.kt`, `NotificationHelper.kt`, `ProfileSetupActivity.kt`, `ScreenCaptureService.kt`, `Constants.kt`, `strings.xml`, `activity_profile_setup.xml`, `LoginView.swift`, `SpiralTracingView.swift`.
- Manually reconstructed 6 files where genuine, real edits (mostly this round's Beanie/activity-inference work) were mixed in right up to the truncation point, so a blind revert would have destroyed real work: `BeanieStatusStore.kt`, `MainActivity.kt`, `BeanieService.kt`, `BeanieDevicePickerActivity.kt` (Android), `BeanieBluetoothService.swift`, `BeanieTemperatureReading.swift` (iOS) — completing each one by hand from where the real content stopped, cross-checked against the corresponding Android/iOS implementation for exact parity (CSV column order, extra-broadcast fields, RTC command payload format, etc.).
- Fixed a handful of smaller pure truncations found in a final sweep: `AndroidManifest.xml`, `activity_beanie_device_picker.xml`, `activity_consent.xml`, `build.gradle.kts`.
- Verified clean with a full repo sweep after the fact: brace-balance and UTF-8 validity across every `.kt`/`.swift` file, XML well-formedness across every `.xml`/`.plist`, and a NUL-byte scan across every source file in both app trees. All clean.

Both apps are now in a complete, internally-consistent state ready to hand to a programmer to build — real compilation still wasn't possible in this sandbox (no Windows-compatible JDK/Android SDK, no Xcode), so a first real build on each platform is the natural next verification step once this reaches someone with the right toolchain.

## Follow-up (July 2026, round 6): pd35 sync verification, keyboard overhaul, fitness-app imports

**Verified an external reviewer's 4 claims against the actual code rather than taking them at face value.** Claim 1 (Kotlin lambda destructuring "compile error" in `PostureCalibrationActivity.kt`) was factually wrong — `List<T>` destructuring up to 5 elements is standard Kotlin, confirmed against Kotlin's own docs — but the applied fix (explicit indexing) was harmless, so left as-is. Claims 2 and 3 (CoreML `.mlmodelc` extension check, Combine-based mirroring + reset hooks in `BeanieBluetoothService.swift`) were real, correct, and already applied by a concurrently-active external editor of this same folder. Claim 4 (a separate `pd35` monorepo was out of sync) required connecting that folder — per instruction, treated as separate from this project, narrow verification only: it was genuinely synced and current (source-level diff confirmed pd35 has the fixed, non-duplicated, non-truncated versions of every file checked), with two exceptions fixed directly in `pd35`: a 377-trailing-NUL-byte corruption in `DataManager.kt` (same pattern as round 5, stripped), and an orphaned, functionally-dead, zero-stub `logic/BeaniePostureEngine.kt` left over from before the real posture engine existed — confirmed via grep it has zero call sites anywhere in pd35, so left in place rather than deleted, consistent with treating pd35 as out of scope for the same cleanup pass pd35-mobile received.

**The keyboard's custom IME/extension isn't just a keyboard — it's the study's typing-dynamics biomarker collector**, logging key class, backspace rate, and word length (never the actual characters) on both platforms. This surfaced mid-task: the request was to replace it with AnySoftKeyboard (Android) / Keyman or AkifKeyboard (iOS), but third-party keyboards run as separate apps and can't write into this app's data store — doing so verbatim would have silently ended that data collection. (AkifKeyboard specifically is also abandoned since 2019, unmaintained, confirmed via its GitHub repo.) Raised this trade-off directly; the direction back was to find a good-UX approach that keeps the PD-tracking intact. A further constraint made that decision concrete: this sandbox's network blocks `codeload.github.com`/`api.github.com`/git-over-HTTPS (confirmed by testing directly), so vendoring a third-party open-source keyboard's source wasn't technically achievable here even setting the data-logging problem aside. Net result: significantly overhauled the in-house keyboard on both platforms instead —

- Added a numbers/symbols page on Android (there wasn't one at all — no way to type a digit or most punctuation without leaving the keyboard) and fixed the equivalent iOS gap, which was subtler: `KeyboardViewController.swift` already had a complete `numRows` layout and `isNumbersMode` flag, but no key anywhere ever set it, so the numbers page was fully unreachable dead code. Both now have a working "?123"/"ABC" toggle.
- Long-press popups for digits (top letter row, matching key columns 1–0 on both platforms for shared muscle memory) and common accents (é/è/ê, ü, í, ñ, ç, etc.) — implemented via `popupCharacters` in Android's Keyboard XML (a built-in feature that wasn't being used), and a custom `UILongPressGestureRecognizer` + overlay popup on iOS (no built-in equivalent there).
- Swipe-left-to-delete-the-whole-previous-word (one gesture instead of many backspace taps — a meaningful win specifically for tremor-affected typing), double-space-for-period with auto-capitalize, and auto-capitalize at the start of a field and after `.`/`!`/`?`.
- Haptic + click-sound feedback on every key, larger/more consistent key sizing (iOS bumped from 38–44pt to 46–50pt to match Android's existing 52dp and the app's established 48dp tremor-friendly tap-target standard), and rounded/outlined keys in the dopa-X palette with a clear filled pressed-state.
- Consolidated two duplicate, drifted "keyboard status" sections that existed side-by-side in iOS `SettingsView.swift` into one.
- All of this is additive to the existing `PDKeyboardService`/`KeyboardViewController` — the keystroke-dynamics logging path (key class, backspace, word length → CSV) is untouched.

**Fitness-app imports: workout imports only (not continuous background sync), covering Apple Health, Health Connect, and Strava**, per the scoping decisions made along the way. All three write into the same `physical_activity.csv` schema, extended (v2, both platforms in lockstep) with `source`/`duration_min`/`calories`/`avg_heart_rate` columns — manual entries fill the new columns `Manual,,,`. The activity-type list itself was also extended from `Running/Bike/Other` to add `Swimming`/`Weight Training`/`Pilates`, matching the specific sports named in the field-feedback that prompted this (running, cycling, swimming, weightlifting, pilates).

- **iOS**: the app already had a `HealthKitManager` doing passive gait-metric sync (walking speed, steadiness, HR/HRV) — extended it with workout reading (`HKWorkout` via `HKSampleQuery`, duration from `totalEnergyBurned`, heart rate via a scoped `HKStatisticsQuery`) rather than building a parallel manager. New "Import from Apple Health" button in the Activity Log screen.
- **Android**: no passive-health integration existed at all. Added Health Connect (`androidx.health.connect:connect-client:1.1.0`, the latest stable release) — new `HealthConnectManager` object, manifest permissions, and a properly-timed `ActivityResultLauncher` (registered at activity-construction time, since Health Connect's permission flow can't be requested lazily from inside a button handler once the activity has started). New "Import from Health Connect" button alongside the existing physical-activity dialog.
- **Strava** (both platforms): full OAuth2 authorization-code flow (`ASWebAuthenticationSession` on iOS — cleanly handles the redirect with no extra deep-link plumbing; a dedicated small `StravaAuthCallbackActivity` on Android, kept separate from `MainActivity` so the main activity doesn't need to become `exported="true"` just for this one redirect), token refresh, and a recent-activities fetch mapped onto the same schema.
- **Setup still required before Strava works, and it's real, non-optional setup**: a free Strava API app has to be registered at strava.com/settings/api for a Client ID/Secret (an account-creation step outside what I can do), and Strava's "Authorization Callback Domain" has to be set to match the `pdcollect://strava-callback` scheme already wired into both manifests. ## Follow-up (July 2026, round 7): final stability/UX audit of the keyboard and fitness-import work

Re-reviewed everything from round 6 with a specific eye for crash risk, edge cases, and cross-platform consistency, since it was the least battle-tested code from this engagement. Found and fixed real bugs on both fronts, plus one significant pre-existing bug unrelated to round 6 that surfaced while checking the new fitness-import CSV columns.

**Highest-impact: a locale bug could have been silently corrupting research CSVs on iOS for a long time, unrelated to this session's changes.** `String(format: "%.1f", value)` on iOS uses the device's *current locale* when no locale is passed — on any region that writes decimals with a comma (much of Europe), that call produces `"45,3"` instead of `"45.3"`, which silently splits a comma-delimited CSV row into an extra column from that point on. Android's equivalent code was already fully guarded against this — every single `String.format` call in the Android tree passes `Locale.US` explicitly, with no exceptions found. iOS had no equivalent discipline: grepped every `String(format:` call across the iOS app and found the locale-sensitive form, unguarded, in every CSV-writing model — `TouchEvent`, `TestResult`, `SensorReading`, `FaceDistanceSample`, `BeanieIMUReading`, `BeanieTemperatureReading`, `HealthKitManager.csvString` (gait metrics), plus this round's own new `PhysicalActivityEvent`. Display-only formatting (dashboard values, motor-test result screens) was deliberately left alone — locale-sensitive number display is correct, desired behavior there. Fixed all seven CSV-writing spots by passing `Locale(identifier: "en_US_POSIX")` explicitly, the same fix already used elsewhere in this codebase for exactly this reason (`KeyboardViewController`'s `Date.dateKey`).

**The iOS keyboard had no shift key at all.** Android's `qwerty.xml` has always had one (row 3, `⇧`); iOS's `KeyboardViewController` never did, in any round — `isUppercase` existed as a variable and had auto-cancel-after-one-letter logic already written in `characterPressed`, but nothing in the UI ever set it true, so a user could never manually capitalize a word that wasn't at a sentence start (a proper noun mid-sentence, for instance). Added a `⇧` key to the last letter row, positioned and sized to match Android's placement, wired to the already-existing (but previously unreachable) toggle logic.

**Auto-capitalize was invisible on both platforms.** Both keyboards silently commit an uppercase letter at the start of a sentence, but neither ever changed what the *keys themselves* displayed — a user would see a lowercase "a" key and get a capital "A" in the text field, with no visual warning either way. Fixed on both: Android now mutates each letter key's `Keyboard.Key.label` directly when shifted (its classic `KeyboardView` doesn't auto-flip label case from `isShifted` the way a hand-built key view does), iOS's key titles now factor in `autoCapNext` alongside the manual shift state. Both also now let an explicit shift-key tap *override* a pending auto-capitalize, so a user can force a deliberately-lowercase word at a sentence start instead of being stuck with the automatic capital.

**Android's shift was accidentally a permanent caps-lock, not the one-shot the code's own comment claimed.** The comment said "a one-shot shift auto-cancels after a single letter, like every mainstream keyboard" but nothing in the code ever reset `isCaps` back to false — once toggled on, it stayed on indefinitely. Fixed to match the documented intent (and iOS's already-correct one-shot behavior): typing one letter while manually shifted now cancels the shift, same as tapping shift on any standard keyboard.

**A multi-character `insertText` call on iOS could silently drop a keystroke-class sample from the logging pipeline.** The double-space-for-period feature inserted `". "` as one two-character call; iOS's keystroke logger is event-driven (`textDidChange` → diff against the previous length → classify the *last* character), so a single call inserting two characters at once only ever produced one log entry, not two — the period's own `punctuation` sample was silently absorbed into the following space's. The same root cause also affects the rare case of a long-press-selected "ß" being auto-capitalized to "SS" (a real two-character expansion) at a sentence start. Fixed at the root: `commitCharacter` and the double-space handler now insert one Unicode character at a time, so every character gets its own `textDidChange` firing and its own log entry, regardless of how many characters a single user action produces. Android's equivalent logging isn't diff-based (each branch explicitly assigns its own `keyClass`), so it was never exposed to this class of bug.

**Strava's "Workout" activity type would have been categorized inconsistently across platforms.** Android's `StravaManager.mapStravaType` treats a Strava type string containing "workout" as Weight Training; iOS's shared `PhysicalActivityEvent.mapExternalType` (used for both HealthKit and Strava) didn't have that keyword, so the same imported activity would land in a different category depending on which phone the participant used. Added the missing keyword to iOS.

**Checked and confirmed already correct, no changes needed:** `android:popupCharacters` is a real, documented `Keyboard.Key` XML attribute (verified against Android's own reference docs before relying on it for the long-press digit/accent popups) — a wrong attribute name here would have been a resource-compilation build error, not a silent bug, so this was worth confirming directly rather than assuming. Also verified the new `physical_activity.csv` v2 schema can't produce a mixed-header file for existing participants: both platforms scope every CSV to a fresh per-day file/directory (`DataManager.getWriter`/`todayDir`), so a day's file written before this update keeps its old 3-column header and rows self-consistently, and every day from this update onward gets the new 7-column version self-consistently — no file ever has old-format rows under a new-format header or vice versa.

**Flagged, not fixed — a real but lower-severity gap:** none of the three workout-import paths (HealthKit, Health Connect, Strava) deduplicate against previously-imported workouts. Each import re-fetches "the last 7 days" and writes everything it finds, so importing more than once within a week will write duplicate rows for any workout that falls in the overlapping window. Closing this properly needs a persisted "last imported through" timestamp per source, checked symmetrically across all four fetch paths (2 platforms × HealthKit-or-HealthConnect + Strava) — a real, bounded task, but a meaningfully bigger change than anything else in this round, so left as a known limitation rather than rushed. Also flagged, not independently re-verifiable here: the Health Connect numeric exercise-type fallback constants (`EXERCISE_TYPE_RUNNING_TREADMILL` etc.) couldn't be checked against a live SDK reference this round (the sandbox's browser tool wasn't connected) — they're a well-established, stable subset of the API and only a fallback behind title-text keyword matching, but worth a quick confirm during integration, as the code's own comment already says.

Same verification discipline as every round above: every touched file re-read in full via the file tools after editing, not trusted from bash or diff. Real compilation still isn't possible in this sandbox.

## Follow-up (July 2026, round 8): closed the duplicate-import gap flagged in round 7

Round 7 flagged, but didn't fix, that none of the three workout-import paths deduplicated against previously-imported workouts — re-importing an overlapping look-back window would write the same workout twice. Closed it on both platforms:

- New `ImportedActivityStore` (SharedPreferences-backed on Android, UserDefaults-backed on iOS) remembers every `"source:externalId"` pair already written to `physical_activity.csv`, capped at 2000 entries (oldest dropped first) so it can't grow unbounded over years of use. Deliberately not scoped to the current profile or cleared on Reset & Withdraw — a stale ID from a previous participant on a reused device is inert, since a new participant's Strava/HealthKit account IDs are globally unique and can't collide with an old one.
- Threaded a stable per-source ID through the existing fetch models — `ExternalActivitySample.externalId` (Android), `PhysicalActivityEvent.externalId` (iOS) — populated from Health Connect's `session.metadata.id`, HealthKit's `workout.uuid`, and Strava's numeric activity `id` on both platforms. Never written to the CSV; bookkeeping only.
- All four import call sites (`doImportFromHealthConnect`/`importFromStrava` on Android, `importFromHealthKit`/`importFromStrava` on iOS) now check-and-skip already-seen IDs, marking each one as imported only once it's actually been written — so even a hypothetical duplicate within a single fetch batch can't slip through. Fails open by design: a workout with a blank/missing ID (which shouldn't happen in practice, but isn't provably impossible) is always imported rather than silently dropped, since losing real data is worse than one unlikely duplicate.
- Import toasts/messages now report the actual new-import count and distinguish "nothing found at all" from "found some, but already imported" — previously both cases would have looked the same to the user once dedup was in place.

## Follow-up (July 2026, round 10): sleep import (Apple Health / Health Connect — Garmin and other apps included)

Added sleep-session import alongside the existing workout import, on both platforms, so nights already tracked by a watch or app (Garmin Connect, Oura, AutoSleep, Samsung Health, Fitbit, or Apple Watch itself) flow in without manual entry. New `sleep.csv` on both platforms, identical schema: `timestamp_ms,source,provider,sleep_start_ms,sleep_end_ms,time_in_bed_min,total_sleep_min,light_min,deep_min,rem_min,awake_min,unspecified_min`. `provider` is the specific app that recorded the night (e.g. "Garmin Connect") — on iOS, HealthKit hands that back directly; on Android, Health Connect only gives a package name, so it's resolved to a friendly label via `PackageManager` with a fallback to the raw package name if that lookup fails.

- **iOS**: `HealthKitManager.fetchRecentSleep()` — the harder side of this, since HealthKit has no "sleep session" object the way it does for workouts; a night comes back as many small per-stage `HKCategorySample`s. Groups them into sessions by starting a new one whenever the gap since the previous sample's end exceeds 60 minutes (bridges brief overnight wake-ups without merging two separate nights), then sums each stage bucket (`asleepCore/asleepDeep/asleepREM/asleepUnspecified/awake/inBed`) into minutes. Sleep-analysis type added to the same `readTypes` set as workouts, so it's covered by one authorization prompt rather than a second one.
- **Android**: `HealthConnectManager.fetchRecentSleepSessions()` — simpler here, since Health Connect already models a night as one `SleepSessionRecord` with a `stages` list. Sums the same stage buckets from Health Connect's `STAGE_TYPE_*` constants. Sleep permission (`READ_SLEEP`) is requested and granted independently of the exercise/calories/heart-rate permissions — denying or never granting one doesn't block the other, via a second, separate `ActivityResultLauncher`.
- Both platforms: dedup via the existing `ImportedActivityStore`, namespaced `"HealthKit-Sleep"` / `"HealthConnect-Sleep"` so the keys can't collide with the workout-import keys in the same store. "Import Sleep" button added next to the existing workout-import buttons (iOS: Activity Log's now-renamed "Import Health Data" section; Android: the same dialog the Health Connect/Strava workout-import buttons already live in).
